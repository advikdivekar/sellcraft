## 1. System design in one paragraph
A Next.js app (the UI) talks only to its own server, which proxies `/api/*` to a FastAPI backend. The backend stores jobs, assets and connections in SQLite, files on disk, and a Shopify token encrypted in a vault. A "generate" request creates a job and runs two lanes at the same time in a background thread: a **visual lane** (measure, cut out, refine, backdrop, render shots) and a **language lane** (build prompts, call the model in parallel parts, check the copy). They meet at the image deck and final video, which need the finished copy. The UI polls the job every 1.5 s and shows real progress and partial copy. See figures 1 and 3.

## 2. The models, and the process each one follows
Details in figure 2. Every model has one job and one strict contract.

| Model or tool | Job | Contract it follows |
|---|---|---|
| **Gemma 3 4B** (Ollama) | Fast copy (default), photo reading | Prompt in 7 sections (FACTS, PLATFORM, TONE, STYLE, OBJECTIVE, RULES, OUTPUT); output constrained by a JSON schema; temperature 0.4 for copy, 0.1 for photos |
| **Gemma 3 12B** (Ollama) | Best-quality copy (opt-in), judge in evaluation | Same prompts and schemas as 4B; as judge, lists statements the facts do not support |
| **rembg, silueta (U2-Net)** | Remove the background | Mask predicted on a copy of at most 1400 px, applied to the full-resolution photo; falls back to a framed photo when coverage is under 4% or over 96% |
| **OpenCV, NumPy, Pillow** | Measure, denoise, 2x super-resolution (FSRCNN), local contrast, backdrop, deck | Deterministic; never repaints the product |
| **FFmpeg** | Video | Camera moves, crossfades, text cards, ffprobe validation; **not** generative video |
| **Qwen3.5-397B-A17B** (Tinker) | Teacher: writes and revises training kits | Revises with the checker's findings, at most 2 rounds |
| **Qwen3.5-4B + LoRA v2** (Tinker) | Fine-tuned copy writer | Trained on the app's own prompt; hosted on Tinker, not wired into the app |
| **Deterministic checker** | Scores and flags | Word lists and number checks (digits and number words); plain code |

## 3. Pipelines
- **Copy** (figure 4): facts → prompt and schema → 4 core parts plus one part per platform, in parallel → merge and coerce → validate (retry a bad call once, redo only missing parts) → code post-check (forbidden words, RISKY, REGULATED) → flags shown to the seller and sent to Sentry as metadata.
- **Photo reading** (figure 5): up to 5 photos, type read from the bytes, shrunk to 768 px, read under strict rules, returned only as suggestions marked "From photo, check it".
- **Studio imagery** (figure 6): measure, cut out, refine the product pixels, fix tone, choose a backdrop from what the photo shows, compose. Outputs: studio still (1080x1350), white marketplace photo, transparent PNG, video layers, deck slides.
- **Video** (figure 7): plan at least 4 shots, render each with FFmpeg (up to 3 at once), crossfade 0.4 s, overlay text cards from the edited copy, validate 10 s plus or minus 0.5 and 1080x1920. A copy edit re-renders only the overlay.

## 4. Optimisations
Figure 8 is the timeline and figure 9 lists every change with its before and after. The largest effects, in order: the Fast default (copy 53 s to 14 s), splitting the kit into parallel parts (one 12B call 90 to 145 s down to 45 to 60 s), and overlapping the two lanes so the wait is the slower lane plus a few seconds. A four-photo kit went from about 100 s to about 18 s in Fast mode. Trade-off: the 4B model gets more claims flagged than 12B; the post-check still catches them, and Best quality is one switch away.

## 5. Training and evaluation
Figures 10 and 11. A strong teacher writes kits, code and an independent judge reject anything that breaks the rules, and only clean kits train a small student. On 60 held-out synthetic products, under one checker: untuned 18%, Gemma 4B 23%, Gemma 12B 45%, v1 65%, v2 **88%** clean kits. The independent judge (n = 30) shows a smaller gain: v2 halves the untuned model's flags (0.43 to 0.20) but the intervals overlap and Gemma 12B is lower still. Caveat: the checker also filtered the training data.

## 6. Observability and privacy
Figure 12. Each model call is a `gen_ai.chat` span, each job a transaction, each flagged claim an issue, each seller report an event. An allow-list scrubber removes everything that is not metadata, and a canary test fails if a planted marker reaches any outgoing payload. Not claimed: that Sentry has caught a production incident.

## 7. Data, API and states
Figure 13. Three tables (`jobs`, `assets`, `connections`), routes grouped by purpose, and the job state machine (`queued`, `generating_copy` with `generating_video`, `assembling_video`, `completed`, `failed`). Files are UUID-named and served only through their job's route.

## 8. Deployment and trust
Figures 14 and 15. Run it on your machine; open it on a phone through a Cloudflare quick tunnel behind an access code (traffic passes Cloudflare, so demos only); or deploy only the landing page with no backend (`NEXT_PUBLIC_DEMO_ONLY=1`, `render.yaml`, live on the Render free plan). Seller data stays local. The only things that can leave are an on-tap Shopify draft and scrubbed Sentry metadata.

## 9. Known limits
- Jobs run in a background thread, so a restart loses an in-flight job; stages are separate functions so they can move to a worker.
- No user accounts: connections belong to the installation, so it is built for one seller.
- The fine-tune is hosted on Tinker and not in the app's path; exporting it to GGUF for Ollama is not done.
- The evaluation set is synthetic and judge n = 30 per model; there is no real-seller result yet.
